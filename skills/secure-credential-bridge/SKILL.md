# Secure Credential Bridge

Use this skill when the user wants Codex to connect to a remote machine or run a remote maintenance operation through the local bridge.

## SSH workflow

1. Call `bridge_status` to see configured host names. It reports names and readiness only.
2. If the local alias is unknown, call `ssh_discover_hosts`. This returns alias names only, reads the local OpenSSH config, and makes no network connection.
3. When a connection check is needed, call `ssh_connect` with one local alias. Reuse a successful check within the current task instead of repeating it before every query. Host addresses and usernames are never accepted as tool arguments. Version 0.1.3 authenticates to one fingerprint-pinned host without a per-call approval prompt and runs no remote command. If setup is missing, the local SSH manager opens so the human can configure it outside Codex.
4. Classify the complete operation using the rules below, then call `ssh_run_command` with the configured alias and the requested command. For clearly read-only queries within the user's requested scope, proceed directly without asking for another conversational confirmation. The plugin independently checks the entire command; an assistant statement that it is read-only does not grant an exemption. For a changing or unsupported command, include `intent_zh`: a concise Chinese sentence describing its actual purpose and impact. The local confirmation window shows that sentence in red bold type, plus the full target and original command. Do not add an extra conversational confirmation when the user has already authorized the operation; the plugin still requires its own confirmation.

Treat a failed or denied call as final for that attempt. Do not guess another host, retry repeatedly, bypass the approval window, or fall back to direct shell/SSH commands. Never put passwords, tokens, or other secrets in remote command arguments because command text is displayed and may be returned in logs/results.

Use only the bridge's configured MCP tools. Host addresses and usernames are stored in the local bridge configuration, and passwords/key passphrases are stored in Windows Credential Manager. Never ask the user to paste an address, username, password, token, private key, or database connection string into chat or tool arguments.

## Capabilities and approval

- `bridge_status` reports configured SSH host and database query names only.
- `ssh_run_command` accepts a command for one configured host, with a 300-second timeout ceiling and bounded output. Apply the read-only policy below instead of requesting confirmation solely because a command runs remotely.
- `email_create_draft` accepts only an exact allowlisted recipient and does not send. `email_send_draft` displays the complete recipient, subject, body, and digest in the configured local approval window before sending. Confirm the digest corresponds to that draft. Delivery failures are not retried automatically; verify the mailbox first because SMTP may have accepted a message before the connection failed.
- `postgres_query` accepts only a configured query name and its declared parameters. Execute permitted read-only queries within the requested scope without additional conversational confirmation. Do not propose arbitrary SQL to bypass the allowlist.

### Read-only queries

The user's request to inspect or diagnose the selected environment authorizes the necessary read-only queries. Do not ask "may I run this query?" before each command, including in production, when the target and scope are already clear. Brief progress updates are sufficient.

Read-only means observing existing state without intentionally changing remote files, configuration, business data, running services, or task execution. Examples include bounded log searches, process and disk status, `docker ps`, `systemctl status nginx --no-pager`, reading relevant non-secret configuration, and configured read-only database queries. Normal access logs generated by a query do not make it a write operation.

Evaluate the whole command and its arguments, every pipeline stage, shell substitution, script, and API call. A command name such as `cat`, `SELECT`, or an HTTP `GET` method alone is insufficient evidence. Writes, output redirection to remote files, restarts, deployment, deletion, task retries/requeues, email delivery, and calls with unknown side effects do not qualify. For mixed operations, run the independent read-only part first and keep the changing part subject to approval. Inspect unknown scripts or command semantics before classifying them; if the side effects remain unclear, retain the approval requirement.

Keep queries bounded and relevant to the user's task. The read-only exception does not authorize retrieving passwords, tokens, private keys, or unrelated sensitive data. Mutating operations retain the existing approval requirements.

### Runtime policy and compatibility

Version 0.1.3 exempts only a conservative, argument-aware list of queries, for example `whoami`, `df -h`, `docker ps`, `docker logs --tail 100 app`, and `systemctl status nginx --no-pager`. Every supported pipeline or `&&` stage must qualify. Unknown commands, arbitrary interpreters/scripts/SQL through SSH, API calls, shell expansion, file redirection, and unsupported flags still require confirmation even when the assistant believes the operation is observational. See the plugin README and `mcp/command_policy.py` for the exact supported subset. This is a policy for trusted POSIX/Linux utilities, not proof about arbitrary remote executables or shell startup files.

`intent_zh` must be a nonempty single-line Chinese description of at most 500 characters. It is required for commands outside the allowlist and never changes classification. Never label a restart, requeue, deletion, or write as a read-only check. For an unsupported diagnostic script, state its diagnostic purpose accurately and let the plugin request approval.

On success the tool returns `read_only` and `approval_required` together with the bounded execution result. These describe policy classification, not independent verification of every side effect. A required approval that is denied, closed, unavailable, invalid, or timed out stops execution before credential resolution/network access. The bundled local mode provides red text; native MCP clients control their own visual styling and receive the Chinese intent in plain text.

Check the actually loaded tool schema. An installed/running version 0.1.2 can still prompt for every SSH operation and has no `intent_zh` field; editing this skill alone does not update that process. Reload after installing the changed plugin. Do not invent skip-approval parameters, auto-click approval windows, or use direct shell/SSH to evade an enforced confirmation. A client timeout does not prove a pending or running command stopped; reconcile its outcome before retrying.

## Credential handling

Credentials are resolved by the local process from Windows Credential Manager. The tools must never return, log, or persist a credential. Configure only non-secret host/account metadata in `config/bridge.json`; place passwords or SSH key passphrases in Credential Manager with `scripts/manage_credential.py` (it prompts without echo and never accepts secrets as command-line arguments). Never ask the user to paste an IP, username, password, token, private key, or passphrase into Codex when a local alias/configuration can be used.

The skill does not create or discover credentials. The human configures the host address, username, pinned host-key fingerprint, and credential reference in the local manager. The MCP server reads its configuration for each tool call, so saving host/credential configuration can be followed by an immediate tool call in the current thread; a new thread is not needed for host configuration. Loading a changed plugin build or new tool definition may still require the MCP plugin to reload.

## Security boundary

This plugin prevents its own MCP tools from returning credentials, but it is not an OS isolation boundary: a local process running as the same Windows user, including another tool with shell access, may be able to read that user's Credential Manager entries. For protection against a compromised model/tool process, move the credential store and adapters into a separate restricted Windows service identity and expose only authenticated, ACL-protected local IPC with the same operation allowlists.
